# Refine step by step; decide with demos

## Begin with needs and community inspiration

Analyze the audience, purpose, object relationships, actions, host design, and device scope. Form a brief, then seek original technical visualizations, product presentations, explorable models, and interactive work. Three.js Showcase, author case studies, Codrops, and GitHub can help discover candidates; open the original work to inspect it.

Select a few relevant, well-finished references. Use [visual design](visual-design.md) to turn actual observations into decisions, retaining titles, authors/URLs, observation methods, and limitations. Popularity and effect counts do not replace aesthetic judgment.

Treat an explicit design language as a constraint. Otherwise, turn references into clear choices and agree on direction before fully modeling. Resolve major differences through the demo process below. If offline, disclose the gap and use project/user references without inventing sources.

## When the user needs to choose

Prepare concrete alternatives for consequential appearance or interaction choices that cannot be resolved from the request, host design, or prior decisions: form language, section versus exterior, realism versus schematic treatment, camera organization, direct dragging versus steps, or labels. Make routine technical choices and fix defects within an agreed direction independently.

Missing exact color values alone do not justify a question; inspect the existing design first. A request for refinement does not authorize an arbitrary visual direction.

## Build comparable candidates

1. State the decision, distinguishing aesthetic language, reading mode, and operation. Keep object facts, information, devices, and core tasks comparable. Known product geometry and technical relationships do not change across depictions of an existing object.
2. Make two or three lightweight but real demos. Aesthetic candidates may differ meaningfully in subject/page scale, viewing distance, light/dark relationships, or material treatment. Reading/interaction candidates may compare exterior versus section or free exploration versus stepwise expansion. Vary what answers the question; do not force theme rotation or maximum difference.
3. Capture appearance at comparable viewports and appropriate angles; provide usable core actions. Explain completion level, placeholders, and intentional camera differences. Do not confuse unequal implementation quality with style. Color, corner, or shadow changes do not automatically create structural differences; if only color comparison was requested, deliver that comparison.
4. Present clear options: name, screenshot/runnable entry, main difference, effect on reading/operation, tradeoff, and recommendation. Do not let the recommendation conceal alternatives; allow combinations or revisions.
5. Review demos before asking. Wait for the user's decision before expanding dependent work; continue independent foundations. Silence or elapsed time is not acceptance.

If demos cannot run or be shown, explain the obstacle. Runnable files or static sketches can still help, but label their inability to establish interaction; prose alone is not a demonstrated choice.

For example, a half-section and a complete exterior can change reading mode while sharing pale backgrounds, metal materials, and UI language. State that scope honestly. If the decision concerns aesthetics, show further composition, lighting, and material alternatives with the same content and core actions.

## Prefer parallel candidate development

When subagents are available, implement independent candidates in parallel. Give them the same brief, content, accuracy/device constraints, reference findings, and explicit individual directions and acceptance criteria. Assign separate directory/file ownership; state that other agents are working and must not be reverted or overwritten. The lead agent owns shared foundations.

The lead agent waits for candidates, personally inspects screenshots and operates core interactions, checks comparable content and completion, then assembles one entry point. Resolve technical failures, missing information, or large fidelity differences before presenting. An agent's completion claim is not acceptance. Give the user concrete differences, reasons, and the choice.

Without delegation, implement sequentially and provide the same comparison. Do not require another plugin or a particular model, or create user-visible tasks as a substitute for internal subagents. Small fixes without a comparison need stay local.

## Preserve the chosen language

Keep minimal useful agreements in the existing brief or design notes: aesthetic intent and references, form/proportion evidence, material roles and lighting goals, camera/narrow-screen composition, and the rhythm of selection/focus/expansion/return. Distinguish chosen from pending decisions and retain explicit preferences and rejections. A proposed candidate is not a user choice.

Reuse host tokens and components, adding missing roles only for real reuse needs. Small fixes do not require a new design system; create a separate design document when cross-page reuse or the user calls for it. Refine within the agreed language instead of rotating fonts, themes, or modeling styles to show activity. When feedback changes direction, explain the effect and update agreements.

## Address the most important current problem

- Present the visible version, default state, relevant actions, and the round's objective.
- Inspect screenshots and operation yourself; identify the main aesthetic/experience defects. Distinguish preference choices, factual errors, and implementation defects in user feedback.
- Name the object, visible defect, and plausible cause, then choose a verifiable correction. Preserve the chosen direction and correct relationships; adding content must not evade an existing problem.
- Compare at comparable viewports, content, and states. If the camera or composition is itself changing, explain it rather than forcing an identical camera. Demonstrate interaction changes and inspect affected selected, expanded, and narrow-screen states. Explain improvement, tradeoffs, and remaining decisions.

For example, if a lens appears almost edge-on by default, first verify the geometry against evidence, then try viewing angle or tonal relationships and compare initial/expanded states. Do not thicken a lens with established real curvature. A brighter highlight alone does not prove better form.

Use the same notes for necessary versions, screenshots, and correction results rather than building a separate process framework. [Verification](verification.md) distinguishes viewed images, actual input, and unverified behavior.

## Converge without an endless loop

Perfection is a shared direction, not a guarantee based on subjective full marks. Deliver the round when the chosen visual direction is realized, obvious aesthetic/interaction defects are resolved, necessary states have been tested, and agreed acceptance conditions are met. Unresolved direction choices remain with the user. Continue fixing clear defects; use candidates for remaining preferences. Without user feedback, deliver the current reviewable version and choices as pending, not finally accepted.

Do not keep increasing polygon counts, material layers, effects, or interactions in pursuit of perfection. A restrained, clear, easy-to-use result can be complete.
